# Security notes

This starter is intentionally fail-closed around authentication and write authorization. Passwords use Node's `scryptSync`, sessions use random tokens stored only as SHA-256 token hashes; browser console sessions are transported in an HttpOnly cookie and the console does not persist the bearer token in localStorage, and operational queries are constrained by `organization_id`.

Invitation tokens are stored as hashes and expire. Customer portal access links are one-time bootstrap credentials; successful exchange rotates the credential into a new scoped HttpOnly portal cookie and the original URL token becomes invalid. Webhook secrets are stored as hashes; webhook creation requires HTTPS and a minimum secret length. Local attachments are stored under an organization-specific path with generated keys and SHA-256 content metadata. API/static responses add browser hardening headers including CSP for the external-script UI; production TLS/HSTS remains a deployment verification responsibility.

As of v0.11.2, every mutating API endpoint enforces API-key scope (`read`/`write`/`admin`/`*`) at the router level, not only via organization role; a `read`-only key cannot perform writes anywhere in the API. This closes a gap found in independent review where a subset of write endpoints checked only organization role (which every API key satisfies) and not the key's granted scope. **Correction in v0.11.3:** that 0.11.2 claim was incomplete — roughly fifteen mutating endpoints were still missing the router-level scope check, and two of them (`revokeSession`, `markNotificationRead`) had no authorization check at all. All are now fixed; see `CHANGELOG.md` (0.11.3) for the endpoint list and `test/security_scopes.test.js` / `test/security_cross_tenant.test.js` for regression coverage.

**v0.11.3 also fixed a critical cross-tenant issue:** an org owner/admin could previously generate a password-reset token for a user belonging to a *different* organization (the lookup checked only that the caller was an admin, not that the target user was a member of the caller's org), and redeem it to take over that account. This is now blocked with a membership check; see `test/security_cross_tenant.test.js`. Treat any "as of vX.Y.Z" security claim in this file the same way — as a statement about what was true when it was written, not a guarantee that no other gap exists. Run your own review before production use.

Password login is now throttled in-process: 8 failed attempts for the same email within 15 minutes locks that email out for 15 minutes, returning `429 LOGIN_RATE_LIMITED`. This is a single-instance mitigation only — a multi-instance deployment needs a shared store (e.g. the buyer's own Redis/Postgres-backed limiter) for this to hold across instances, same as the existing API rate-limit boundary.

Before production deployment, independently verify TLS termination and proxy behavior, distributed rate limiting, CSRF strategy for cookie-based deployments, secret storage, dependency/supply-chain status, backups/restores, PostgreSQL permissions/RLS, monitoring and infrastructure hardening.

No external email, webhook, S3-compatible storage or identity provider delivery is asserted without a real integration test in the buyer environment.
