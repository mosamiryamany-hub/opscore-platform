# OpsCore — تشغيل العميل في وقت قياسي

## المتطلبات
- Node.js 22.23.4 (Node 22.x)
- نسخة ZIP موثوقة مع بيان الإصدار وبصمة SHA-256
- مشروع PostgreSQL/Neon مستقل للاختبار أولًا، ثم مشروع إنتاج منفصل
- مشروع استضافة مؤهل للاستخدام التجاري؛ تحقّق من شروط خطة الاستضافة الحالية قبل البيع

## 1) قاعدة البيانات (PostgreSQL/Neon)
1. ابدأ بفرع/قاعدة اختبار فارغة؛ لا تختبر ترحيلات الإصدار على قاعدة إنتاج.
2. طبّق ملفات الترحيل الموجودة فعليًا داخل الحزمة من `backend/sql/postgres/` حسب ترتيب أسماء الملفات الرقمي، ولا تتجاوز أي ملف موجود. استخدم القائمة الفعلية داخل نسخة OPSCORE.zip المستلمة بدل الاعتماد على قائمة محفوظة من إصدار أقدم.
3. لا تستخدم `backend/db/` بوصفه مجلد الترحيلات؛ يحتوي ملفات مخطط/مساندة وليس مجموعة الترحيلات المرقّمة.
4. استخدم دور تطبيق محدودًا مثل `opscore_app`، مع `rolsuper=false` و`rolbypassrls=false`، ولا تستخدم دور مالك قاعدة البيانات أو `opscore_gate` ذي الامتيازات العالية للتطبيق.
5. احفظ رابط الاتصال في متغير بيئة سري `DATABASE_URL` أو `OPSC_DATABASE_URL`، ولا تضع الأسرار في المستودع أو في سجلات الطرفية.

## 2) تثبيت وتشغيل الحزمة
1. فكّ الحزمة في مجلد جديد وتحقق من بصمتها مقابل `dist/COMMERCIAL_RELEASE_STATEMENT.json` و`dist/SHA256SUMS.txt` من نفس Pipeline.
2. من جذر المستودع نفّذ `npm ci --ignore-scripts` لتثبيت برنامج تشغيل PostgreSQL المقفول `pg@8.23.1`، ثم داخل `backend/` نفّذ `npm ci --ignore-scripts --omit=peer`. لا تستخدم `npm install --no-package-lock` ولا تثبيتًا عابرًا لنسخة `pg`.
3. اضبط `DATABASE_ENGINE=postgres` و`DATABASE_URL` لدور التطبيق قبل تشغيل أوامر التهيئة.
4. شغّل `npm run bootstrap` بعد التأكد من أن قاعدة الاختبار فارغة. أمر bootstrap يستخدم مُهيّئ الاتصال المشترك `db-open` ويجب أن يختار محرك PostgreSQL فعليًا عند إعداد PostgreSQL.
5. نفّذ الاختبارات المحددة في بيان الإصدار، ثم اختبر النسخ الاحتياطي والاستعادة في بيئة اختبار منفصلة.

## 3) إعداد الاستضافة
متغيرات البيئة المطلوبة بحسب البيئة:
- `DATABASE_URL` أو `OPSC_DATABASE_URL`: رابط PostgreSQL لدور التطبيق الأقل صلاحية
- `DATABASE_ENGINE=postgres`
- `NODE_ENV=production`

يستخدم إعداد Vercel الحالي تثبيتًا مقفولًا بواسطة `npm ci`. لا تنسخ أسرار بيئة التطوير إلى الإنتاج. تحقق من أن النشر يشير إلى commit المقصود وأن قاعدة البيانات المستهدفة هي القاعدة الصحيحة.

## 4) أول تشغيل والتحقق
1. تحقق من `GET /api/health` وأن `engine=postgres`.
2. نفّذ bootstrap مرة واحدة فقط على قاعدة فارغة.
3. سجّل الدخول بحساب المالك الذي أنشأته أثناء bootstrap.
4. اختبر حدود صلاحيات المستخدمين وعزل مؤسستين مستقلتين قبل قبول البيانات الحقيقية.

## 5) أدلة وحدود الاعتماد
- نجاح CI لا يثبت وحده نجاح تثبيت العميل أو سلامة قاعدة إنتاجه.
- أدلة PostgreSQL المعزولة لا تمثل شهادة إنتاج.
- لا تُعتبر النسخ الاحتياطية/الاستعادة مثبتة حتى تُختبر على بيئة العميل.
- ترجمات الذكاء الاصطناعي قد تحتوي أخطاء؛ لا توجد ضمانة مراجعة بشرية/لغوية لكل لغة.
- توقيع تطبيقي الهاتف وحسابات المتاجر والنشر والمفاتيح والتكاملات الخارجية وتراخيص الخرائط والكول سنتر مسؤولية العميل.
- آخر تدقيق مثبت للشجرة المقفلة: صفر ثغرات حرجة، وصفر عالية، و10 متوسطة، و2 منخفضة. تمنع CI النتائج العالية والحرجة؛ تظل المتوسطة والمنخفضة معلنة وتُرفق ملفات JSON الكاملة في خط إنشاء الحزمة.
- `productionCertification` و`productionIsolationCertification` يظلان غير معتمدين ما لم توجد أدلة مستقلة حديثة تخص النشر الفعلي.

## 6) سلامة الإنتاج
لا تنفّذ ترحيلات على قاعدة الإنتاج أو نشرًا إنتاجيًا لمجرد اتباع هذا الدليل. يتطلب ذلك قرار تغيير مستقل، ونسخة احتياطية قابلة للاستعادة، وخطة تراجع، والتحقق من commit والبيئة المستهدفة.
