# محرك التوأم الرقمي متعدد المجالات — OpsCore FIELD

## النطاق المنفذ في المرشح الحالي

## الخريطة المعمارية الموسعة

الخريطة متعددة المراحل والمراجع التقنية المستهدفة ومصفوفة الأدلة المحدثة موجودة في [`DIGITAL_TWIN_SYSTEM_MAP_2026-10-21_AR.md`](./DIGITAL_TWIN_SYSTEM_MAP_2026-10-21_AR.md)، ومعها ملف JSON قابل للمعالجة الآلية. الخريطة تميز بين التنفيذ المحلي والعقد الساكن والخطط التي لم تُنفذ؛ لا تعتبر ذكر معيار أو مشروع مفتوح المصدر دليلًا على تكامل فعلي.

هذا التنفيذ يجمع بين نواة عامة حتمية وطبقة توأم تشغيلي متصلة بقاعدة بيانات OpsCore الحالية. لا يفترض أن النظام FTTH فقط؛ الأنواع والمجالات لا تزال بيانات يحددها التطبيق أو الجهة المشغلة.

### 1) النواة العامة: `backend/src/digital-twin-core.js`

- هوية للتوأم تشمل المؤسسة ومعرّف التوأم ونوع الكيان والتصنيف والحالة وبصمة SHA-256 حتمية مستقلة عن ترتيب المفاتيح.
- تطبيع صارم لحمولة الختم: رفض القيم التي تضيع أو تتغير عند التحويل، مثل `undefined` و`NaN` و`Infinity` وBigInt والدوال والدورات المرجعية والـ getters والمفاتيح الرمزية والمصفوفات المتناثرة وخصائص المصفوفة الإضافية والأنواع ذات النماذج الأولية المخصصة، مع حدود للعمق وعدد العقد وحجم الحمولة.
- حالة مستنسخة ومجمّدة بعمق لمنع تعديل البيانات المتداخلة بعد تكوين بصمتها.
- فحص حداثة القياسات: حديثة أو متقادمة أو مؤرخة في المستقبل، مع رفض القياسات المستقبلية خارج هامش السياسة، ورفض المفاتيح المكررة وتحديد الحد الأقصى لعدد القياسات.
- سلسلة أحداث مرتبطة بـ `previousHash` و`hash` داخل الذاكرة، مع حد لحجم الحمولة وعدد الأحداث؛ القيم المعادة للمستدعي منفصلة عن السجلات الداخلية.
- تقييم حدود قابل للتفسير؛ القواعد الغائبة أو القيم المفقودة تنتج `UNKNOWN` لا نجاحًا مفترضًا، كما تُرفض الحدود المتناقضة.
- التصريحات `physicalStateVerified=false` و`providerConnected=false` و`productionReady=false` باقية عمدًا حتى تتوفر أدلة مستقلة.

### 2) التوأم التشغيلي المحفوظ

دالة `store.platformTwin(ctx)` موجودة في `backend/src/platform-intelligence-layer.js`، وأصبحت لقطة الحالة تحمل `opscore.operational-twin.v2`. وهي تتضمن ملخصات مؤسسية بحسب حالة أوامر العمل والأصول والمواعيد والمهام التشغيلية، وخطط الصيانة، وأحداث الأصول، والفواتير، وتسليمات التكامل، بالإضافة إلى توزيع الأولويات وأنواع الأصول وإشارات مثل الأعمال المتأخرة، والأعمال العاجلة، وفشل التكامل، وفشل الأصول خلال آخر 30 يومًا.

المجاميع مقيدة بـ `organization_id` في الاستعلامات. تُحفظ اللقطات في `operational_twin_snapshots`، وتُربط بأحداث سلسلة دائمة في `operational_twin_chain_events`. أُضيف ترحيل قاعدة بيانات رقم 28؛ حفظ اللقطة وإضافة حدث السلسلة يجريان داخل المعاملة الحالية إن وجدت، أو ضمن معاملة SQLite مستقلة عند الاستدعاء المباشر.

### 3) التحقق والتاريخ وواجهات HTTP

- `POST /api/v1/platform/twin/snapshots`: إنشاء لقطة محفوظة ثم التحقق من اتساق بصمتها.
- `GET /api/v1/platform/twin/snapshots`: عرض تاريخ المؤسسة مع حد أقصى للنتائج ومؤشر متابعة.
- `GET /api/v1/platform/twin/snapshots/:id/verify`: إعادة حساب البصمة والتحقق من اتساق JSON وملخص العدّادات وربط اللقطة بحدث السلسلة ونطاق المؤسسة.
- `GET /api/v1/platform/twin/integrity`: فحص سلسلة أحداث المؤسسة من البداية، بما يشمل التسلسل، و`previous_hash`، وبصمة الحدث، ووجود اللقطات المقابلة، واكتشاف اللقطات التي لا يقابلها حدث سلسلة.
- `GET /api/v1/platform/twin`: يظل مسار القراءة الحالي موجودًا، وتظل نتيجة التوأم الحالية متوافقة مع استدعاءات الطبقة التشغيلية الحالية من حيث الحقول الأساسية السابقة.

التوثيق/الصلاحيات ما زالت تمر عبر سياق المصادقة و`requireScope`، كما أن استعلامات التاريخ والتحقق لا تبحث إلا داخل المؤسسة الحالية؛ المعرف من مؤسسة أخرى يعامل كأنه غير موجود.

### 4) الختم الرقمي القابل للتحقق المستقل — `backend/src/digital-twin-seal.js`

- ينشئ غلاف DSSE باستخدام Pre-Authentication Encoding (PAE) ويوقّع حمولة رأس السلسلة بمفتاح Ed25519.
- يتضمن محتوى الختم المؤسسة، وتسلسل/بصمة رأس السلسلة، وعدد الأحداث واللقطات، ووقت الإصدار، ومعرّف المفتاح، وبصمة المفتاح العام، وبصمة الختم السابق الاختيارية.
- `createDigitalTwinSealWithSigner()` يقبل موصل توقيع بعيد؛ يتحقق من التوقيع بالمفتاح العام قبل إصدار envelope. هذا حد تكامل فقط، وليس موصل KMS/HSM من مزود فعلي.
- `backend/scripts/verify-digital-twin-seal.js` أداة مستقلة للتحقق من ملف envelope بالمفتاح العام الموثوق، دون الحاجة إلى المفتاح الخاص.
- verifier يرفض كذلك payload موقعة تتجاوز حدود الإصدار، مثل الادعاء بأن الختم منشور خارجيًا أو أن الاحتفاظ غير قابل للتعديل أو أن التعديل بواسطة مسؤول قاعدة البيانات أصبح مستحيلًا. هذه الادعاءات تظل `false` حتى يُثبتها نظام خارجي فعلي مستقل.
- `publishDigitalTwinSeal()` عقد نشر يتحقق من شكل الإيصال وادعاء الاحتفاظ غير القابل للتعديل. لم يوصل مزود تخزين/شفافية حقيقي؛ لذلك لا يوجد إثبات نشر خارجي فعلي، ولا يُوثق بـ `providerClaimsIndependentlyVerified=true`.

### 5) عقد PostgreSQL/RLS وبوابة الإثبات الحي

- تم توحيد عقد سياق المؤسسة في `backend/src/adapters/postgres.js`: يضبط الموصل `app.tenant_id` الذي تقرؤه سياسات RLS، ويزيل مفاتيح السياق البديلة أيضًا قبل إعادة الاتصال إلى المسبح.
- الاختبارات المحلية تتحقق من العقد والتنظيف الاحتياطي، لكنها لا تثبت سلوك خادم PostgreSQL الحقيقي.
- `npm run db:postgres-live-rls` يشغّل ترحيل سلسلة التوأم في مخطط مؤقت داخل قاعدة اختبار، ثم يختبر القراءة/الإدراج/التحديث/الحذف بين مؤسستين ودورًا غير مالك ولا يملك `BYPASSRLS`، وغياب سياق المؤسسة. يتراجع الاختبار عن معاملته.
- أُضيف `.github/workflows/digital-twin-postgres-live.yml` بخدمة `postgres:18` وعمليات GitHub Actions مثبتة ببصمات commit كاملة، لتشغيل البوابة على pull request أو يدويًا بعد رفع الحزمة إلى مستودع. لم يُشغّل هذا الـworkflow داخل هذه الجلسة، فلا توجد نتيجة CI حية حتى الآن.
- نتيجة البيئة الحالية في `backend/docs/verification/POSTGRES_LIVE_RLS_RESULT.json` هي `UNVERIFIED` لأن `OPSC_PG_TEST_URL` ومشغل `pg` وخدمة PostgreSQL غير متاحة في بيئة التنفيذ الحالية. وجود بوابة قابلة للتشغيل لا يُعد نجاحًا حيًا.

## ما الذي يثبته التحقق — وما الذي لا يثبته

**يثبته الاختبار المحلي:** النواة الحتمية، وسلامة المدخلات، وكشف بعض أنواع العبث، وتسلسل الأحداث، وتكافؤ مخطط PostgreSQL ساكنًا، وعقد سياق المؤسسة، والتوقيع/التحقق من DSSE بمفتاح Ed25519، ورفض التوقيعات أو الحمولات المعدّلة، والتحقق من واجهة signer بعيدة محاكية. هذه اختبارات محلية وليست إثبات تكامل مورد خارجي.

**لا يثبته:** التوقيع المحلي لا يعادل KMS/HSM، وحد النشر لا يثبت أن مزودًا خارجيًا حفظ الختم. توقيع الرأس وحده لا يثبت صحة البيانات الفيزيائية الداخلة. لا يوجد حتى الآن إثبات PostgreSQL/RLS حي، أو اتصال بأجهزة استشعار/IoT/SCADA، أو GIS/BIM/ERP فعلي، أو محاكاة فيزيائية/ثلاثية الأبعاد، أو تنبؤ أعطال مُعاير ببيانات واقعية. مسؤول قاعدة بيانات كامل الصلاحيات يستطيع إعادة كتابة السلسلة الداخلية؛ مقاومة ذلك تعتمد على توقيع بمفتاح مستقل وختم خارجي حقيقي وسياسة احتفاظ موثقة.

## الاختبارات المحلية والبوابة الحية

من مجلد `backend`:

```sh
node --test test/digital-twin-core.test.js test/platform_intelligence_layer.test.js test/digital_twin_seal.test.js test/postgres_rls_context_contract.test.js
```

ولتشغيل اختبار PostgreSQL الحي على **قاعدة مخصصة للاختبار فقط**، وبعد تثبيت peer dependency المعتمدة `pg` وتوفير صلاحية إنشاء دور/مخطط اختبار:

```sh
OPSC_PG_TEST_URL='postgresql://.../opscore_test' npm run db:postgres-live-rls
```

لا تمرر رابط الإنتاج. تعود البوابة بحالة `UNVERIFIED` عند غياب شروطها، ولا تعتبر الاختبارات الساكنة بديلًا عنها. نجاح المجموعة المحلية لا يمثل اعتمادًا إنتاجيًا.
