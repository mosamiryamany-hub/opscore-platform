# تقرير تنفيذ وتحقق — OpsCore FIELD Digital Twin System Map

**تاريخ التحقق:** 2026-10-21  
**الإصدار:** 0.11.62 — Digital Twin System Map Candidate  
**الحكم:** مرشح هندسي مُحسّن؛ ليس اعتماد إنتاجي نهائي.

## ما تم تنفيذه

0. إصلاح عقد سياق PostgreSQL: كان الموصل يضبط `app.current_tenant_id` و`app.organization_id` بينما سياسة العزل تقرأ `app.tenant_id`. أصبح الموصل يضبط المفتاح المقروء من السياسة ويزيل جميع الأسماء البديلة قبل إعادة الاتصال إلى المسبح.
0. إضافة `digital-twin-seal.js`: ختم DSSE/Ed25519 محلي، محول signer بعيد يتحقق من توقيعه قبل الاستخدام، وأداة CLI للتحقق بالمفتاح العام. واجهة النشر الخارجية عقد فقط، لا يوجد مزود KMS/HSM أو immutable storage متصل.
0. إضافة بوابة `db:postgres-live-rls` التي تتحقق من ترحيل جدول السلسلة والعزل والعمليات السلبية داخل مخطط مؤقت قابل للتراجع. حالة تشغيلها في بيئة هذه الحزمة `UNVERIFIED` لعدم توفر URL/driver/server؛ لا تُعامل كبوابة ناجحة.

1. سد فجوة تكافؤ مخطط PostgreSQL لجدول `operational_twin_chain_events` بإضافته إلى المخطط الأساسي وترحيل `031_digital_twin_chain_hardening.sql`.
2. إدراج جدول سلسلة التوأم ضمن `ENABLE ROW LEVEL SECURITY` و`FORCE ROW LEVEL SECURITY` وسياسة المؤسسة، مع تعريف دالة tenant context داخل الترحيل كي لا يعتمد على ملف إعداد منفصل عند تطبيق المهاجرات بالترتيب.
3. تقوية فحص التكافؤ ليقارن كل جداول SQLite مع مخطط PostgreSQL ومجموعة المهاجرات ويكشف فجوات تغطية RLS لجدول سلسلة التوأم.
4. إضافة خريطة هندسية متعددة المجالات، وملف JSON قابل للقراءة الآلية يميز التنفيذ المحلي من العقود الساكنة والخطط غير المنفذة.
5. الحفاظ على حدود التوأم: بياناته التشغيلية مشتقة من سجلات المؤسسة؛ لا ادعاء اتصال بأجهزة حقيقية أو محاكاة فيزيائية أو تنبؤ مُعاير أو ختم خارجي مستقل.

## نتائج التحقق

- **مجموعة الإصدار السابقة:** `PASS` — 380/380 عبر 94 ملف اختبار على Node `22.16.0`، لكن هذه النتيجة سبقت إضافة اختبارات ختم DSSE وحراس سياق PostgreSQL؛ نتيجة العدد الجديد تُحدد فقط بعد آخر تشغيل أدناه.
- **اختبارات مركزة بعد إضافة ختم DSSE وعقد سياق PostgreSQL:** 30/30 ناجحة في آخر تشغيل محلي.
- **تكافؤ المخطط الساكن:** `PASS` — 127 جدولًا في SQLite، و127 في مخطط PostgreSQL الأساسي، و127 في مجموعة المهاجرات؛ لا توجد فجوات في قوائم النقص أو تغطية RLS التي يفحصها السكربت.
- **بوابات الحراسة المحددة:** حياد المجالات، تشديد الإصدار، سياسة حدود التعديل، إصدار Node، وتنظيف مرفقات التشغيل: `PASS`.
- **سلامة الأرشيف السابق:** CRC سليم، 493 ملفًا في البيان، صفر اختلافات SHA-256/حجم. يلزم إعادة إنشاء البيان والتحقق بعد آخر التعديلات.

## ما لم يُثبت

- لم يُشغّل PostgreSQL حي في بيئة التنفيذ الحالية؛ لا تتوفر خدمة/أدوات PostgreSQL أو Docker/Podman. لذلك لا يوجد ادعاء بنجاح RLS حي أو اختبار التزامن أو صلاحيات الأدوار الفعلية.
- لم يُربط KMS/HSM أو ختم زمني/سجل خارجي مستقل برأس السلسلة.
- لم تُربط حساسات أو IoT/SCADA/GIS/BIM/ERP حقيقية.
- لا توجد محاكاة فيزيائية ثلاثية الأبعاد أو تنبؤ أعطال مؤهل ببيانات حقيقية.
- لم يُعتمد المنتج للإنتاج؛ فحص المخطط الساكن واختبارات SQLite لا يعادلان تأهيل بيئة تشغيل العميل.

## ملف التسليم

- بصمة/حجم الحزمة النهائية: يملآن فقط بعد بناء الأرشيف الجديد وفحص محتواه؛ قيم الحزمة السابقة لم تعد صالحة بعد التعديلات.
- الحزمة تتضمن `INTEGRATED_PACKAGE_MANIFEST.json` و`INTEGRATED_SHA256SUMS.txt`، وخريطة التصميم بالعربية بصيغتي Markdown وJSON.

## الخطوة التالية المطلوبة قبل اعتماد PostgreSQL

تطبيق المهاجرات على PostgreSQL حقيقي بإصدار مثبت، باستخدام دور migrator منفصل عن runtime، ثم اختبارات عزل سلبية/إيجابية لمؤسستين، وغياب سياق المؤسسة، ومالك الجدول و`BYPASSRLS`، وتزامن إضافة أحداث السلسلة. بعدها فقط يمكن تحديث حالة بوابة PostgreSQL من `NOT_RUN` إلى نتيجة موثقة.


## ختم السلسلة وحدوده

اختبارات محلية لوحدة DSSE/Ed25519 تتحقق من الحمولات والتوقيعات والمفتاح، ويعمل verifier مستقل بالمفتاح العام. هذا يثبت صحة التوقيع المحلي فقط. لم يتم الاتصال بمزود KMS/HSM أو بخدمة تخزين/شفافية خارجية، وإيصال النشر ليس مثبتًا من طرف ثالث. لا ترفع تفاصيل تشغيلية حساسة إلى سجل شفافية عام دون تقييم الخصوصية.
